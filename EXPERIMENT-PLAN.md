# Experimental Plan: Workload-Aware SQL Result Caching for Concurrent Agents

## 1. Objective and Scope

We investigate three decisions in a shared SQL result cache:

1. **Query normalization:** How should SQL queries be canonicalized so equivalent requests reuse cached results without introducing incorrect cache hits?
2. **Invalidation and refresh:** How can the system identify cached results affected by database writes, and which invalidated results are worth proactively recomputing?
3. **Cache eviction:** When cache capacity is limited, which cached results should be retained to maximize future computational savings?

The overarching objective is to minimize cumulative SQL tool-wait time, database work, and cache-management overhead while preserving correctness.

### System assumptions

- Multiple agents operate concurrently against the same logical PostgreSQL database.
- All agents access a shared SQL broker and shared Redis result cache.
- Database writes are reported through a common CDC/invalidation pipeline.
- SQL queries are generated externally; the agent and underlying language model are treated as **black boxes**.
- The broker can observe SQL text, parameters, execution time, result size, request timestamps, cache hits, and relevant database updates.
- Agents do not directly manipulate the result cache.
- Experiments initially use one PostgreSQL primary to isolate the cache algorithms from replica-lag effects. Replicas can be introduced in a later robustness experiment.

These experiments concern caching complete SQL results. They do not initially investigate caching intermediate execution plans, database pages, partial query results, or model KV states.

### Important separation

The project distinguishes:

- **Correctness:** A cached result affected by a committed write must not be served once that write is required to be visible under the chosen consistency contract.
- **Selection:** Determine which cached entries may have changed.
- **Management:** Decide whether invalidated entries deserve immediate recomputation, later recomputation, or permanent removal from the current cache population.

Frequency and execution-cost heuristics are used for management, not to justify serving known-stale results.

## 2. Common Experimental Infrastructure

All three research tracks should use a common execution framework so that results can be compared.

### 2.1 Architecture

The proposed system consists of:

**SQL request source → SQL broker → Redis cache / PostgreSQL**

PostgreSQL also produces database-change events that are consumed by the invalidation component.

The SQL request source can be either a running SQL agent or a replay of previously collected tool-call traces.

For most experiments, trace replay is preferable. It allows deterministic comparisons across cache policies without introducing variation from the language model.

### 2.2 Workload construction

Use two complementary workload classes.

**Workload A: Recorded SQL-agent traces**

Collect SQL calls generated by agents operating against one database, including:

- Schema exploration.
- Specific-row lookups.
- Filtered queries.
- Aggregations.
- Joins.
- Nested queries.
- Repeated and semantically similar requests.

The purpose is to evaluate how policies behave on actual agent-produced SQL.

**Workload B: Controlled shared-database workloads**

Construct a continuous sequence of concurrent reads and database writes.

Generate or replay enough requests against one logical database to obtain meaningful reuse and invalidation behavior.

CH-benCHmark, which combines transactional updates and analytical queries over shared tables, is a candidate source of realistic database operations. Recorded SQL-agent queries can be added to the same database where feasible.

The controlled workload should allow independent variation of:

| Variable | Suggested configurations |
|---|---|
| Concurrent clients | 1, 8, 32, 64 |
| Write proportion | 0%, 1%, 5%, 20% |
| Query popularity | Uniform, moderately skewed, highly skewed |
| Query repetition | Low, medium, high |
| Write locality | Random, concentrated on popular data |
| Query-cost distribution | Mostly cheap, mixed, expensive analytical queries |
| Cache capacity | Unlimited, 25%, 10%, 5%, 1% of the unbounded working-set size |
| Access pattern | Stationary, bursty, shifting popularity |

These values are proposed experimental settings, not observations about existing workloads.

Real traces and synthetic variations must be reported separately, since artificially increasing repetition can exaggerate the apparent usefulness of caching.

### 2.3 Instrumentation and shared metadata

Maintain the following information for every query identity:

| Metadata | Definition |
|---|---|
| Query key | Canonical SQL identity, including relevant parameters and execution context |
| Frequency | Number of historical requests |
| Execution time | Estimated PostgreSQL execution time on a miss |
| Last access | Timestamp of the most recent request |
| Decayed frequency | Frequency estimate that reduces the weight of old requests |
| Reuse before invalidation | Historical or predicted number of requests before the next relevant write |
| Cache status | Valid, invalid, absent, or currently refreshing |
| Result size | Bytes occupied by the cached result |
| Dependencies | Tables, columns, and predicates needed for invalidation |

Result size is treated as a physical capacity constraint, not as an additional predictive heuristic.

The five primary heuristic dimensions investigated in Tracks 2 and 3 are:

1. Frequency.
2. Query execution time.
3. Recency.
4. Reuse before invalidation.
5. Frequency decay.

Metadata should be maintained consistently across policies and should not automatically disappear when a cached value is invalidated or evicted. Otherwise, an LFU-based policy would repeatedly lose the popularity history of frequently invalidated queries.

### 2.4 Common correctness rules

Only eligible, deterministic, read-only queries should be considered for ordinary result caching.

Queries containing volatile functions, untrusted user-defined functions, row-locking clauses, session-dependent behavior, or unsupported SQL constructs should bypass caching unless their semantics are explicitly modeled.

Cache identity must also distinguish relevant database identity, parameters, authorization context, schema resolution, and session settings.

All policies should use the same concurrency-safe cache-fill mechanism and the same PostgreSQL change stream.

This prevents differences in consistency implementation from contaminating comparisons of policy decisions.

# 3. Experiment Track 1 — SQL Query Normalization

## RQ1: How much additional cache reuse does query normalization provide, and what are its correctness and processing costs?

### Motivation

Two SQL statements may have identical semantics but different text.

For example:

```sql
SELECT balance FROM accounts WHERE id = 42;
```

and:

```sql
select balance
from accounts
where id=42;
```

These should ideally map to the same result-cache key.

However, aggressive normalization can incorrectly merge queries with different semantics.

The central trade-off is between improving cache reuse and preventing false equivalences.

### Hypotheses

**H1.1:** Conservative SQL-aware normalization substantially reduces duplicate cache entries relative to exact-string matching.

**H1.2:** PostgreSQL-aware AST normalization captures most syntactic variation without the need for general semantic rewriting.

**H1.3:** LLM-assisted semantic normalization can identify additional equivalences beyond syntactic canonicalization, but its benefits depend on correctness, inference overhead, and the amount of additional reuse discovered.

## Experiment 1A — Compare normalization strategies

Compare the following approaches:

| Policy | Description |
|---|---|
| N0: Raw SQL | Exact string matching; no normalization |
| N1: Conservative lexical | Normalize safe whitespace and keyword casing while preserving literals and quoted identifiers |
| N2: SQLGlot | PostgreSQL-dialect parsing and conservative AST serialization |
| N3: LLM-assisted semantic normalization | Use a reasoning model to identify semantically equivalent SQL expressions, with independent validation before merging cache identities |

All strategies execute the original submitted SQL. Canonicalization is used only to determine cache identity.

For N3, the LLM may identify equivalences beyond simple formatting differences, such as:

- Equivalent boolean predicates.
- Equivalent join formulations.
- Reordered commutative conditions.
- Queries equivalent under known schema constraints.
- Alternative SQL formulations producing the same result.

However, an LLM-proposed equivalence is not automatically accepted. Validation must establish sufficient correctness guarantees, using schema constraints, supported equivalence rules, or other sound verification mechanisms.

Execution-based testing can detect incorrect equivalences, but matching query results on a finite set of database states does not prove equivalence for all future states.

### Dataset construction

Create two evaluation sets.

**Set A — Controlled SQL equivalence tests**

Start from valid SQL queries and generate known-safe syntactic variations:

- Different capitalization of keywords.
- Different whitespace and line breaks.
- Redundant parentheses where semantics are preserved.
- Equivalent formatting.
- Safe identifier spelling variations.
- Semantically equivalent predicates.
- Equivalent SQL expressions under specified schema constraints.

Also construct deliberately non-equivalent query pairs:

- Different string literals.
- Different numeric values.
- Quoted versus unquoted identifiers.
- Different `ORDER BY` and `LIMIT` behavior.
- Different operators and casts.
- PostgreSQL-specific constructs.
- Queries with different schema resolution or session context.

These negative pairs are important because an overly aggressive normalizer might merge them.

**Set B — Actual agent SQL**

Collect a large sample of SQL calls from the chosen agent workload.

Measure how often distinct raw SQL strings normalize into the same canonical representation.

Evaluate these queries under multiple database states where possible, rather than comparing results on only one snapshot.

## Experiment 1B — Correctness validation

For every group of distinct SQL strings mapped to the same cache key, check whether the mapping is justified.

For testing, execute the original statements against the same PostgreSQL snapshots and session settings.

Where result ordering is not guaranteed by SQL, compare using appropriate multiset semantics rather than raw output order. Compare result types and column metadata as well.

A collision is dangerous if two queries share a key despite having different results or observable behavior in some relevant database state.

Execution-based testing can detect incorrect equivalences, but matching on several snapshots does not prove general semantic equivalence.

Therefore, unverified semantic rewrites should not be admitted into the correctness-critical production cache.

### Metrics

| Metric | Meaning |
|---|---|
| Canonicalization coverage | Percentage of eligible queries successfully normalized |
| Key reduction | Reduction in distinct cache keys |
| Additional hit rate | Cache hits gained relative to raw SQL keys |
| Cost-weighted hit improvement | Additional database execution time avoided |
| False-equivalence count | Incorrectly merged query pairs |
| Normalization overhead | p50/p95/p99 processing time |
| Unsupported-query rate | Queries requiring fallback or cache bypass |
| End-to-end savings | Tool-wait time saved after paying normalization overhead |

A key reduction alone is insufficient: merging two rarely accessed queries provides little benefit.

## Experiment 1C — When is normalization worth its cost?

Run identical read traces under N0–N3, using the same cache capacity and invalidation policy.

Measure how many additional hits normalization creates, and whether those hits justify the per-request processing overhead.

Repeat for workloads with different amounts of syntactic and semantic variation.

**Possible outcomes:**

- If N1 captures nearly all additional hits, more sophisticated canonicalization may provide little benefit.
- If N2 substantially outperforms N1 with low overhead, AST normalization is justified.
- If N3 identifies significant additional reuse, LLM-assisted semantic normalization may be worthwhile, especially for expensive queries.
- If N3 improves reuse but adds excessive inference latency, offline normalization or asynchronous equivalence discovery may be preferable.
- If normalization adds almost no hits to real traces, exact-string caching may be sufficient.

### Main results to present

1. Distinct cache keys before and after normalization.
2. Cache-hit improvement versus normalization overhead.
3. Failure and false-equivalence rates by SQL construct.
4. Database execution time avoided by each normalization strategy.
5. Additional semantically equivalent queries discovered by LLM-assisted normalization.

**Track 1 deliverable:** A measured, correctness-oriented choice of canonicalization strategy for the SQL broker.

# 4. Experiment Track 2 — Cache Invalidation and Refresh

This track contains two related but distinct problems.

- **2A:** Determine which cached query results might have changed after a write.
- **2B:** Among those invalidated results, determine which deserve proactive recomputation.

The five workload heuristics primarily influence 2B. Dependency analysis governs 2A.

## RQ2A: How much unnecessary invalidation can increasingly precise dependency analysis eliminate, and at what computational cost?

### Hypotheses

**H2A.1:** Table-level invalidation unnecessarily discards a substantial fraction of valid cached results.

**H2A.2:** Column- and predicate-aware invalidation preserve more cached results, especially when writes are concentrated on specific rows or columns.

**H2A.3:** The benefit of finer-grained invalidation depends on the additional decision latency and dependency-index maintenance overhead.

## Experiment 2A — Compare invalidation-selection algorithms

All algorithms receive the same database-write events.

| Policy | Invalidation method |
|---|---|
| I0: Full flush | Invalidate every cached query after a write |
| I1: Table-level | Invalidate queries depending on modified tables |
| I2: Column-level | Exclude queries provably unaffected by modified columns |
| I3: Predicate-aware | Use modified row values and query predicates to exclude unaffected results |
| I4: Revision counters | Use query-dependent revision counters rather than eagerly enumerating every affected key |

For I1–I3, maintain reverse dependency indexes so each database update does not require scanning every cached entry.

I4 can be implemented for a restricted query subset based on the 2023 single-table revision-counter method. Unsupported SQL should fall back to a conservative policy.

### Example

Cached results:

```sql
-- Q1
SELECT balance FROM accounts WHERE id = 42;

-- Q2
SELECT balance FROM accounts WHERE id = 100;

-- Q3
SELECT SUM(balance) FROM accounts;
```

Database write:

```sql
UPDATE accounts
SET balance = 200
WHERE id = 42;
```

Table-level invalidation discards all three.

A sufficiently precise predicate-aware method can retain Q2, while Q1 and Q3 require invalidation if their results change.

For complex joins, nested queries, aggregates, and unsupported predicates, the algorithm must remain conservative.

### Ground-truth construction

For a manageable offline workload, establish the actual set of changed query results.

For each write:

1. Record the results of relevant cached queries against the pre-write database snapshot.
2. Apply and commit the write.
3. Reexecute the queries against the corresponding post-write state.
4. Identify which query results actually changed.
5. Compare each invalidation algorithm's decisions against this set.

The offline oracle must evaluate a well-defined sequence of database states. Concurrent live executions are evaluated separately.

Let:

- A = queries whose results actually change.
- I = queries selected for invalidation.

Correctness requires that A is a subset of I.

The objective is to reduce unnecessary invalidations without missing genuinely affected queries.

### Metrics

| Metric | Objective |
|---|---|
| Missed invalidations | Zero for supported, correctness-preserving algorithms |
| Unnecessary invalidations | Minimize |
| Invalidation precision | Maximize fraction of invalidated entries that actually changed |
| Invalidation decision latency | Minimize |
| Metadata/index overhead | Minimize |
| Entries examined per write | Minimize |
| Validity-preserving hit improvement | Maximize |
| Database recomputation avoided | Maximize |

Also report results separately for point lookups, range queries, joins, aggregates, and unsupported constructs.

### Experimental variations

Compare all policies under:

- Low versus high write rates.
- Writes to popular versus unpopular rows.
- Writes to referenced versus unreferenced columns.
- Point lookups versus analytical aggregations.
- Small versus large numbers of cached queries.
- High versus low overlap between query predicates.

Keep cache capacity unlimited during the initial comparison to avoid conflating invalidation decisions with memory-pressure eviction.

### Expected result

This experiment identifies the point at which more precise invalidation stops providing enough additional reuse to justify its cost.

It also determines how much of the workload can be safely handled by each method.

## RQ2B: Once a cached result is invalidated, should it be recomputed immediately, lazily recomputed, or removed from the cache population?

### Motivation

Suppose Q1 is requested 1,000 times per hour while Q2 is requested only twice.

Both are invalidated by a database write.

Immediately recomputing both may waste database resources because Q2 may never be requested again before another write.

However, immediately refreshing Q1 might reduce latency for many subsequent requests.

This is the problem of **refresh prioritization and admission after invalidation**.

### Hypotheses

**H2B.1:** Frequency-based refresh selection reduces unnecessary recomputation relative to eagerly refreshing every invalidated result.

**H2B.2:** Execution cost, recency, and decayed popularity improve decisions over lifetime frequency alone.

**H2B.3:** Predicting reuse before the next invalidation is more informative than predicting overall query popularity.

## Experiment 2B — Compare refresh policies

Fix the invalidation-selection algorithm, initially using I1 or I2, and compare the following management policies.

| Policy | Behavior |
|---|---|
| R0: No eager refresh | Invalidate results; recompute only on a future miss |
| R1: Always refresh | Immediately recompute every invalidated result |
| R2: Frequency | Prioritize entries with highest historical frequency |
| R3: Execution time | Prioritize expensive queries |
| R4: Recency | Prioritize recently requested queries |
| R5: Decayed frequency | Prioritize queries with sustained recent demand |
| R6: Reuse-before-invalidation | Prioritize entries predicted to be requested before becoming invalid again |
| R7: Combined heuristic | Use multiple signals to select refresh candidates |

An invalidated entry that is not eagerly refreshed must be inaccessible to cache lookups.

For R0 and related policies, distinguish two alternatives:

- **Lazy recomputation:** Retain metadata and admit the result again after the next miss.
- **Drop and reconsider admission:** Retain limited historical statistics, but do not automatically cache the next execution unless the admission policy predicts sufficient reuse.

Without this distinction, “delete” and “lazy refresh” are effectively the same policy when every cache miss automatically repopulates the cache.

### Feature definitions

For each query q:

**Frequency:** Total number of historical requests.

**Execution time:** Historical estimate of the cost of running q directly against PostgreSQL. Use a moving estimate derived from genuine executions; do not introduce mandatory extra queries merely to measure cost.

**Recency:** Time since q was last requested.

**Decayed frequency:** Popularity with old accesses discounted. One possible update rule is:

`F_decay(q) = F_decay(q) × exp(-Δt / τ) + 1`

where τ controls how quickly old popularity loses influence.

**Reuse before invalidation:** Estimate how many requests q will receive before the next relevant database modification.

For a simple stationary model, using estimated request rate λ and relevant invalidation rate μ:

`Expected requests before invalidation ≈ λ / μ`

This estimate must be capped or handled separately when μ is near zero, and a fixed prediction horizon should be used for nonstationary workloads.

A useful related quantity is:

`P(next read before next invalidation) = λ / (λ + μ)`

under independent exponential arrival assumptions.

These quantities can be estimated using historical events, without looking ahead into the future portion of the benchmark.

### Proposed combined refresh policy

For an invalidated query, estimate:

`Refresh priority = Expected latency benefit of having the result ready - Expected refresh cost`

A simple implementation could estimate expected demand from decayed frequency and recency, estimate the likelihood of surviving until that demand from write history, and weight the benefit by measured query execution time.

Refresh candidates would be ranked by this score.

If refresh capacity is limited, recompute only the highest-value candidates.

One important consideration: eager refresh usually cannot reduce total database executions relative to a perfect lazy strategy. Its main advantage is moving work away from the critical path of a future read, potentially improving request latency. Its disadvantage is wasted recomputation when the entry is invalidated again before reuse.

Therefore, total database work and request latency must be evaluated separately.

## Experiment 2C — Study refresh behavior under changing workloads

Use controlled workload distributions:

**Scenario A: Stable popularity**

A small number of queries remain highly popular.

Expected advantage: Frequency-based refresh may work well.

**Scenario B: Popularity shifts**

A query is highly popular initially but becomes rarely requested, while another becomes popular.

Expected advantage: Frequency decay and recency may outperform lifetime frequency.

**Scenario C: Frequent writes to hot data**

Popular queries are repeatedly invalidated.

Expected advantage: Reuse-before-invalidation estimates may prevent wasteful refreshes.

**Scenario D: Expensive, infrequently accessed queries**

Some queries are computationally expensive but requested only occasionally.

Expected advantage: Execution-cost weighting may justify precomputation when demand is predictable, although low reuse may still favor lazy execution.

**Scenario E: Bursty concurrent requests**

Multiple requests arrive shortly after a write invalidates a popular query.

Test whether eager refresh reduces tail latency, and whether a lazy policy using in-flight query coalescing can achieve similar benefits with less database work.

### Metrics

- Number of proactive refresh executions.
- Percentage of proactive refreshes used before the next invalidation.
- Wasted refresh work.
- PostgreSQL execution time spent on refreshes.
- Cache hit rate after writes.
- p50/p95/p99 request latency.
- Cumulative tool-wait time.
- Number of on-demand recomputations.
- Refresh scheduling and metadata overhead.
- Correctness violations.
- Time between invalidation and availability of a refreshed entry.

Refreshes must be version-checked so that an older in-progress refresh cannot repopulate the cache after a newer write.

### Main results to present

1. Useful versus wasted refreshes by policy.
2. Tool latency versus additional database work.
3. Refresh effectiveness under changing write frequencies.
4. Ablation showing the contribution of each heuristic.
5. Results with and without refresh-computation budgets.

**Track 2 deliverable:** A comparison of correctness-preserving invalidation methods, plus a workload-aware policy deciding which invalidated results merit recomputation.

# 5. Experiment Track 3 — Cache Eviction and Replacement

## RQ3: Under limited cache capacity, which cached results should be retained to minimize future database work and SQL tool-wait time?

### Motivation

Traditional replacement algorithms prioritize recency or frequency.

However, SQL query results have different recomputation costs and validity lifetimes.

A query that takes two seconds to execute may be more valuable than one that takes two milliseconds, even if it is requested less frequently.

Similarly, a very popular result may not deserve cache space if it is almost immediately invalidated after every refresh.

The central question is whether a workload-aware policy can outperform LRU, LFU, and existing cost-aware caching algorithms.

### Hypotheses

**H3.1:** Execution-cost-aware eviction reduces total database execution time compared with policies that optimize hit rate alone.

**H3.2:** Frequency decay and recency improve adaptation to changing query popularity.

**H3.3:** Incorporating expected reuse before invalidation improves performance in mutable SQL workloads.

**H3.4:** No single heuristic dominates across all workload distributions.

## Experiment 3A — Baseline eviction policies

Compare the following cache replacement policies using identical request traces and memory budgets.

| Policy | Primary signal |
|---|---|
| E0: FIFO | Insertion order |
| E1: LRU | Recency |
| E2: LFU | Lifetime frequency |
| E3: Decayed LFU | Frequency decay |
| E4: Cost-only | Historical query execution time |
| E5: Frequency × cost | Popularity weighted by recomputation cost |
| E6: GDSF | Frequency, fetch cost, size, and aging |
| E7: Reuse-aware | Expected requests before invalidation |
| E8: Combined heuristic | Frequency, execution time, recency, frequency decay, and reuse before invalidation |

GDSF is an important established baseline because it already incorporates several of the proposed signals.

Its benefit score is commonly based on a combination of frequency, fetching cost, object size, and an aging term.

Custom heuristics should therefore be compared against GDSF, not just LRU and LFU.

### Experimental method

1. Start with an empty cache.
2. Replay the same query sequence for every policy.
3. Execute a query against PostgreSQL on a miss, or use a previously measured cost in a controlled simulator.
4. Insert the result according to a fixed admission rule.
5. When capacity is exceeded, select the eviction victim according to the active policy.
6. Record the resulting hits, misses, database executions, eviction decisions, and timing.

Measure both cold-start and steady-state behavior.

Initial comparisons can use read-only traces to isolate eviction behavior. For policies involving reuse before invalidation, use traces containing writes and a fixed correctness-preserving invalidation mechanism, with all other conditions held constant.

### Metrics

| Metric | Reason |
|---|---|
| Hit rate | Measures successful reuse |
| Byte hit rate | Accounts for different result sizes |
| Total PostgreSQL execution time | Measures actual computational savings |
| Cost-weighted miss ratio | Penalizes misses on expensive queries |
| Cache occupancy | Measures memory utilization |
| Eviction rate | Indicates cache churn |
| Tool-wait time | Measures effect on request latency |
| Policy decision overhead | Measures complexity of replacement |
| Metadata memory | Measures hidden costs of sophisticated policies |

**Total avoided execution cost should be the primary metric**, not hit rate alone.

An algorithm achieving fewer hits can still be superior if it preserves more expensive queries.

## Experiment 3B — Vary cache capacity

Repeat the comparison with different memory budgets.

Suggested capacities: 1%, 5%, 10%, 25%, and 50% of the working-set size measured during an unlimited-cache replay.

Ensure the same absolute byte budget is enforced across policies.

Expected behavior to investigate:

- Under very tight capacity, cost- and frequency-aware policies may provide greater benefits.
- With generous capacity, policies may converge because almost all valuable entries fit.
- Algorithms with high metadata overhead may become less attractive when the result cache itself is small.
- Large results may crowd out numerous smaller entries, making size-adjusted value estimates important.

## Experiment 3C — Vary query access distributions

Evaluate at least four scenarios.

**Scenario A: Highly skewed popularity**

A small set of SQL queries accounts for most requests.

Test whether LFU or GDSF approaches the best achievable performance.

**Scenario B: Uniform popularity**

Queries are accessed with approximately equal frequency.

Test whether execution cost becomes more influential than frequency.

**Scenario C: Sudden popularity shifts**

Popular queries become cold and previously cold queries become hot.

Compare lifetime frequency against decayed frequency and recency.

**Scenario D: Cost-popularity disagreement**

Construct a workload where highly popular queries are cheap and expensive queries are less common.

This directly tests whether execution-cost weighting produces better total savings than hit-rate optimization.

### Main results to present

1. Hit rate versus cache capacity.
2. Total database execution time versus cache capacity.
3. Policy performance under changing query popularity.
4. Cost-weighted miss ratio under heterogeneous query costs.
5. Contribution of individual heuristics, including reuse before invalidation.
6. Replacement overhead versus computational savings.

**Track 3 deliverable:** A cost- and workload-aware cache replacement policy evaluated against strong conventional baselines.

# 6. Evaluation Methodology and Fairness

## 6.1 Deterministic trace replay

Record each operation with:

- Request ID and client ID.
- SQL text and bound parameters.
- Database identity.
- Request timestamp.
- Operation type.
- Database state/version information where available.
- Execution time.
- Result size and result digest.
- Commit information for writes.

Replay the same operations and arrival schedule under each policy.

For experiments that do not require the model to remain in the loop, this removes LLM inference variability and substantially reduces benchmark cost.

An offline replay evaluates SQL-level performance and correctness. It does not automatically measure how a live agent might alter its future tool calls after observing different outputs.

## 6.2 Timing methodology

Use two evaluation modes.

**Offline simulation**

Replay traces with recorded or estimated query costs. This allows rapid exploration of many policies, capacities, and workload distributions.

**Live PostgreSQL + Redis execution**

Validate the most promising policies using actual concurrent requests.

The live evaluation should include network latency, parsing overhead, cache lookup time, database execution, refresh work, CDC handling, and queueing.

Offline estimates should not be presented as measured end-to-end speedups.

## 6.3 Correctness verification

For normalization, validate key equivalences against PostgreSQL and maintain conservative fallback behavior.

For invalidation, compare predicted affected queries against a pre/post-write oracle on a manageable set of states.

For refresh, use atomic version checks to prevent stale in-flight recomputations from repopulating the cache.

For live tests, measure temporary staleness caused by asynchronous CDC separately from missed invalidations caused by dependency-selection errors.

All correctness-critical policies should fail conservatively.

## 6.4 Workload splits and statistics

Use chronologically separated segments for policy tuning and evaluation.

Decay parameters, refresh thresholds, and utility-score weights must be selected without knowledge of future test events.

Repeat controlled synthetic experiments across multiple random seeds.

Report confidence intervals or variability for the primary metrics rather than relying only on a single run.

Use identical PostgreSQL data, relevant indexes, request mixes, warm-up conditions, and hardware configurations when comparing algorithms.

Record the cold-start and steady-state results separately.

## 6.5 Metadata overhead

All methods must account for their full memory footprint.

This includes:

- Cached values.
- Query metadata.
- Historical counters.
- Dependency indexes.
- Version counters.
- Eviction data structures.

If using Redis's built-in LRU/LFU as baselines and implementing custom eviction policies in the broker, use a separate protected metadata namespace or store.

Otherwise, Redis might automatically evict bookkeeping needed for correctness, invalidation, or policy evaluation.

# 7. Final Research Questions

The experimental study can be summarized as three research questions.

**RQ1 — Normalization**

How much additional SQL result-cache reuse is enabled by increasingly sophisticated query canonicalization, including LLM-assisted semantic normalization, and what correctness and latency overhead does it introduce?

**RQ2 — Invalidation and Refresh**

How much unnecessary recomputation can dependency-aware invalidation eliminate, and can historical query demand, execution cost, recency, and expected reuse before invalidation guide proactive refresh decisions?

**RQ3 — Eviction**

Can workload-aware replacement using frequency, execution cost, recency, frequency decay, and expected reuse before invalidation outperform conventional LRU, LFU, and GDSF policies?

The central evaluation objective is not simply to maximize cache hit rate. It is to maximize useful computational work avoided, after subtracting the cost of normalization, invalidation, refresh, eviction, and metadata maintenance.
