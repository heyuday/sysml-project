RQ2B/C · Prioritizing refresh after a write

The four-entry budget limits each write, not the total number of refreshes in flight. R0 waits for demand; uncapped R1 refreshes every invalidated resident entry. R2–R7 rank entries. Decay time was fixed at 2 s and prediction horizon at 3 s for these short traces. Unlimited value capacity isolates refresh from eviction. Modeled foreground wait sums only waiting for demand SQL or an in-flight fill; it excludes Python normalization overhead and live contention. Used means subsequently consumed; unused at the trace boundary is reported separately.

Scope and reproducibility

The stable mutable arm reused the calibrated quantity-write trace from the RQ2A pilot. Other arms used the preserved CH warehouse and new calibration. RQ2 hot writes were 20%; the other mutable traces used 5%. The rare-expensive template deliberately uses recurrent stock aggregates so it can be reused and invalidated. The same generated arrivals, SQL, parameters and calibrated costs were replayed within each scenario. All modeled valid cache hits were checked against recorded read digests; stale hit count was zero. A single seed, one order of live trials, one warehouse and short traces provide pilot evidence rather than confidence intervals.

The evidence archive includes the input and calibrated traces, configuration and per-write decisions, full replay summaries, fresh live broker logs, and pilot drivers. decision and result data include R0 drop/reconsider and individual feature ablations. The high-resolution live run is the reported run.
